## Part 1: The Architecture — Transformers

### Before Transformers (Why They Were Needed)

Old approaches (RNNs, LSTMs) processed text **sequentially** — word by word, left to right. Problems:
- Couldn't parallelize (slow training)
- "Forgot" early words by the time they reached later ones (vanishing gradient)
- Struggled with long-range dependencies ("The cat, which sat on the mat that was in the room... **was** black")

### The Transformer (2017, "Attention Is All You Need")

The breakthrough: **process all tokens simultaneously**, and let each token "attend to" every other token.

```
Input: "The cat sat on the mat"

Traditional RNN:  The → cat → sat → on → the → mat  (sequential, slow)

Transformer:      [The, cat, sat, on, the, mat]      (parallel, fast)
                   ↕    ↕    ↕    ↕    ↕    ↕       (all attend to all)
```

### Self-Attention: The Core Mechanism

Each token creates three vectors:
- **Query (Q)**: "What am I looking for?"
- **Key (K)**: "What do I contain?"
- **Value (V)**: "What information do I provide?"

Attention score between token A and token B:
```
score(A, B) = (Q_A · K_B) / √d_k
```

Then softmax normalizes scores → weighted sum of Values.

**Why this matters for agents:**
- The model can relate "it" back to "the weather in Tokyo" across 50 tokens
- But attention degrades with distance → **context window limits are real**
- Multi-head attention (multiple Q/K/V sets) captures different relationship types

### The Full Architecture (Simplified)

```
Input tokens
    ↓
[Token Embeddings + Positional Encodings]
    ↓
┌─────────────────────────────────┐
│  Transformer Block × N layers   │  (GPT-4: ~120 layers estimated)
│  ┌───────────────────────────┐  │
│  │  Multi-Head Self-Attention │  │  ← tokens talk to each other
│  │  + Residual Connection     │  │
│  │  + Layer Normalization     │  │
│  ├───────────────────────────┤  │
│  │  Feed-Forward Network      │  │  ← individual token processing
│  │  + Residual Connection     │  │
│  │  + Layer Normalization     │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
    ↓
[Output Logits → Softmax → Next Token Probabilities]
```

**Key insight:** GPT models are **decoder-only** (causal attention — can only look LEFT). This is why they generate left-to-right and can't "see" what comes after.

## Part 2: Tokenization — The Atomic Unit

### What is a Token?

LLMs don't see "words." They see **tokens** — chunks of text determined by the tokenizer.

```
"Hello, world!" → ["Hello", ",", " world", "!"]     (4 tokens)
"Unbelievable"   → ["Un", "believ", "able"]          (3 tokens)
"こんにちは"      → ["こん", "に", "ち", "は"]         (4 tokens)
```

### OpenAI's Tokenizer (tiktoken)

```python
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")

tokens = enc.encode("Agentic AI is transforming software")
print(tokens)        # [19368, 14970, 1690, 374, 25937, 7845, 5903]
print(len(tokens))   # 7 tokens for 6 words

# Decode back
print(enc.decode(tokens))  # "Agentic AI is transforming software"
```

### Why Tokenization Matters for Agents

| Concern | Impact |
|---------|--------|
| **Cost** | You pay per token, not per word. "Hello" = 1 token. "Pneumonoultramicroscopicsilicovolcanoconiosis" = ~15 tokens |
| **Context window** | 128K tokens ≈ 96K words ≈ 300 pages. Sounds big, but agent conversations with tool results fill it fast |
| **Multilingual** | Non-English text uses more tokens per word → higher cost |
| **Code** | Code tokenizes differently than prose. `function_calling_demo.py` ≈ 8 tokens |
| **Tool results** | A Wikipedia API response might be 2000+ tokens. Budget accordingly |

### Token Math for Agent Design

```
System prompt:          ~200 tokens
Conversation history:   ~500 tokens per exchange
Tool call request:      ~50 tokens
Tool result:            ~500-3000 tokens (varies wildly!)
Final response:         ~200-500 tokens

A 5-turn agent conversation with 3 tool calls:
≈ 200 + (5 × 500) + (3 × 50) + (3 × 1500) + 500 = ~7,850 tokens
```

This is why **context management** (Lesson 3.3) is critical.

## Part 3: The Training Pipeline

### Stage 1: Pre-training (The Expensive Part)

**What:** Predict the next token on ~13 trillion tokens of internet text.
**Cost:** ~$100M+ for frontier models
**Result:** A "base model" that can complete text but doesn't follow instructions well.

```
Input:  "The capital of France is"
Target: " Paris"
Loss:   -log(P(" Paris" | context))  ← cross-entropy loss
```

The model learns:
- Grammar, syntax, spelling
- Facts (compressed into weights)
- Reasoning patterns (from seeing millions of examples)
- Code patterns (from GitHub, Stack Overflow)

**What it does NOT learn:** How to be helpful, safe, or follow instructions.

### Stage 2: Supervised Fine-Tuning (SFT)

**What:** Train on ~100K high-quality (instruction, response) pairs written by humans.
**Result:** Model learns to follow instructions, format responses, be helpful.

```
Instruction: "Explain quantum computing in simple terms"
Response:    "Imagine a regular computer is like a light switch..."
```

### Stage 3: RLHF (Reinforcement Learning from Human Feedback)

**What:**
1. Generate multiple responses to the same prompt
2. Humans rank them (best → worst)
3. Train a "reward model" to predict human preferences
4. Use PPO (reinforcement learning) to optimize the LLM against the reward model

**Result:** Model becomes helpful, harmless, honest. Also: more verbose, more cautious, more "assistant-like."

### Why This Matters for Agents

- **SFT bias:** Models are trained to be "helpful" → they'll try to answer even when they should say "I need to use a tool"
- **RLHF bias:** Models are trained to be cautious → they may over-explain or hedge when you want decisive action
- **System prompts work** because SFT taught the model to follow instructions
- **Function calling works** because the model was specifically fine-tuned on tool-use examples

## Part 4: Inference — What Happens When You Call the API

### The Generation Process

```python
# When you call:
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What is 2+2?"}],
    temperature=0.7
)
```

What actually happens:

```
1. Tokenize input → [token_ids]
2. Pass through ~120 transformer layers
3. Get logits (raw scores) for ALL ~100K tokens in vocabulary
4. Apply temperature: logits / temperature
5. Apply top-p: keep only tokens whose cumulative prob ≤ p
6. Sample from remaining distribution
7. Append chosen token to sequence
8. Repeat from step 2 (with new token added)
9. Stop when EOS token generated or max_tokens reached
```

### Temperature: The Creativity Knob

```
Temperature = 0.0:  Always pick the highest-probability token (deterministic)
Temperature = 0.7:  Moderate randomness (good for most tasks)
Temperature = 1.0:  Full distribution sampling (creative, unpredictable)
Temperature = 2.0:  Very random (nearly incoherent)
```

**For agents:** Use `temperature=0` or `0.1` for tool calls (you want reliable, deterministic function selection). Use `0.7` for creative final responses.

### Top-p (Nucleus Sampling)

Instead of considering ALL tokens, only consider the smallest set whose probabilities sum to p.

```
Vocabulary probabilities for next token:
"Paris":  0.45  ← cumulative: 0.45
"Lyon":   0.20  ← cumulative: 0.65
"Berlin": 0.10  ← cumulative: 0.75  ← top-p=0.75 cuts here
"Tokyo":  0.05
...
```

With `top_p=0.75`, only "Paris", "Lyon", "Berlin" are candidates.

## Part 5: Context Windows — The Working Memory

### What It Actually Is

The context window is the **maximum number of tokens the model can process in one call**. It's not "memory" — it's the entire input the model sees.

```
┌─────────────────────────────────────────────────────────┐
│                    CONTEXT WINDOW (128K tokens)           │
│                                                          │
│  [System Prompt] [Message 1] [Message 2] ... [Message N] │
│                                                          │
│  Everything the model "knows" for this response          │
│  is WITHIN this window. Nothing else exists.             │
└─────────────────────────────────────────────────────────┘
```

### Model Context Windows (2024-2025)

| Model | Context Window | Practical Limit |
|-------|---------------|-----------------|
| GPT-4o | 128K tokens | ~96K words |
| GPT-4o-mini | 128K tokens | ~96K words |
| Claude 3.5 Sonnet | 200K tokens | ~150K words |
| Gemini 1.5 Pro | 1M tokens | ~750K words |
| Llama 3.1 | 128K tokens | ~96K words |

### The "Lost in the Middle" Problem

Research shows LLMs pay **most attention to the beginning and end** of context, and less to the middle:

```
Attention strength across context window:

HIGH  │██                              ██
      │████                          ████
      │██████                      ██████
LOW   │████████████████████████████████████
      └──────────────────────────────────────
       START          MIDDLE           END
```

**Agent design implication:** Put critical instructions at the START (system prompt) and END (most recent message) of context. Don't bury important info in the middle of a long conversation.

### Context Window Management Strategies

| Strategy | When to Use |
|----------|-------------|
| **Sliding window** | Drop oldest messages when approaching limit |
| **Summarization** | Compress old messages into a summary |
| **RAG** | Don't put everything in context — retrieve only what's relevant |
| **Hierarchical** | Summarize tool results before adding to context |

## Part 6: Why LLMs Hallucinate (It's Structural)

### The Root Cause

LLMs are trained to **minimize next-token prediction loss**, not to be truthful. These are different objectives.

```
Training signal: "Given this context, what token comes next?"
NOT:            "Given this context, what is TRUE?"
```

When the model doesn't "know" something, it doesn't output "I don't know." It outputs whatever token sequence is most *probable* given the pattern. And probable ≠ true.

### Types of Hallucination

| Type | Example | Cause |
|------|---------|-------|
| **Factual** | "The Eiffel Tower is in London" | Compressed facts get mixed up |
| **Citation** | Invents paper titles/DOIs | Pattern-matching "what a citation looks like" |
| **Logical** | Correct premises, wrong conclusion | Pattern completion ≠ reasoning |
| **Temporal** | Claims about events after training cutoff | No awareness of its own knowledge boundary |

### Why This Matters for Agents

This is **the core reason agents need tools:**

```
Without tools: LLM guesses from compressed, possibly-wrong training data
With tools:    LLM calls get_weather("Tokyo") → gets REAL current data
```

**Agent design principle:** Never trust the LLM for factual claims that can be verified with a tool. The agent's job is to DECIDE which tool to call, not to know the answer.

## Part 7: What LLMs Actually "Know"

### Knowledge is Compressed into Weights

A 70B parameter model stores ~140GB of floating-point numbers. All "knowledge" is encoded as patterns in these weights.

```
Training data:  "The mitochondria is the powerhouse of the cell"
Encoded as:     Weight patterns that make "powerhouse" highly probable
                after "mitochondria is the"
```

### Implications

1. **Knowledge is lossy** — like a compression algorithm, details get lost
2. **Knowledge has no source** — the model can't tell you WHERE it learned something
3. **Knowledge has no timestamp** — the model doesn't know when it learned something
4. **Knowledge is pattern-based** — it "knows" things that appear frequently in training data better than rare things
5. **Knowledge can't be updated** — without retraining, the model's knowledge is frozen

### The Agent Solution

```
LLM's role in an agent:     REASONING + DECISION MAKING
Tools' role:                FACTUAL KNOWLEDGE + CURRENT DATA
RAG's role:                 DOMAIN-SPECIFIC KNOWLEDGE
Memory's role:              CONVERSATION HISTORY + USER PREFERENCES
```

This separation is the **fundamental architecture of every agent system.**

## Part 8: Practical Implications for Agent Building

### Model Selection Guide

| Use Case | Best Model | Why |
|----------|-----------|-----|
| Agent tool selection | GPT-4o / Claude 3.5 | Best instruction following + function calling |
| High-volume simple tasks | GPT-4o-mini | 10x cheaper, fast, good enough |
| Long document processing | Gemini 1.5 Pro | 1M token context |
| Code generation | Claude 3.5 Sonnet / GPT-4o | Best code benchmarks |
| Local/private deployment | Llama 3.1 70B | Open weights, run on your hardware |

### Cost Awareness

```
GPT-4o:       $2.50 / 1M input tokens,  $10.00 / 1M output tokens
GPT-4o-mini:  $0.15 / 1M input tokens,  $0.60 / 1M output tokens

A typical agent interaction (5 turns, 3 tool calls):
  Input:  ~8,000 tokens  → $0.02 (GPT-4o) or $0.0012 (mini)
  Output: ~2,000 tokens  → $0.02 (GPT-4o) or $0.0012 (mini)

1000 users × 10 interactions/day:
  GPT-4o:      ~$400/day
  GPT-4o-mini: ~$24/day
```

**This is why model selection and token management are engineering decisions, not afterthoughts.**

## Part 9: The Mental Model (Updated)

```
An LLM is NOT:
  ✗ A database of facts
  ✗ A reasoning engine
  ✗ A conscious entity
  ✗ A search engine

An LLM IS:
  ✓ A pattern completion engine trained on internet-scale text
  ✓ Extremely good at "what would a helpful expert say next?"
  ✓ A compressed representation of human writing patterns
  ✓ A tool that, given the right context, produces remarkably useful output
```

### The Agent Equation

```
Agent = LLM (pattern engine)
      + Tools (grounding in reality)
      + Memory (persistence across time)
      + Planning (decomposition of complex goals)
      + Guardrails (safety, cost, reliability)
```

The LLM is the **brain**, but a brain without hands, eyes, and memory is just a person hallucinating in a dark room. **Your job as an agent developer is to build the body.**
